# Build log

Every piece of Ahab (originally Perro) in detail: how it works, why it's built that way, what testing found, and the gotchas met on the way. It's the long version. [STATUS.md](STATUS.md) is the short one (where things stand and what's next), and [ANATOMY.md](ANATOMY.md) is the overview. Add a piece here when it lands; correct an entry when it changes rather than appending history, since Git keeps that.

**Naming note (19 October 2026):** The software and code repository were renamed **Ahab**; the owner's continuing assistant is **Pip**. The descriptions below keep their historical *Perro* references; the code took the new names on 20 October ("Perro becomes Ahab in the code").

## The pieces

Forked from Lobo's runtime (`../Lobo`, commit `2076c5d`). None of Lobo's `home/` came along, so Perro's memory started empty. Perro is the software; each install's agent can have its own name. The owner's is called Pip (since 2026-10-18), with its home in `silascroe/pip`.

**Character.** [AGENTS.md](../AGENTS.md), the README and the heartbeat prompt (`PROMPT_BODY` in `perro/heartbeat.py`) describe a personal assistant in the spirit of Muse or OpenClaw. It does work you hand it, takes initiative within its own tools, is good to just talk to, and has a personality. An earlier draft was too strict, close to "speak when spoken to"; the current wording is deliberately looser.

**Identity files** (modelled loosely on Muse's core files, built one at a time). Four files in `home/workspace/`, all shown at the top of every wake-up page and capped at 8,000 characters each (AGENTS.md at 10,000, MEMORY.md at 20,000) (`perro/identity.py`). `SOUL.md` is who Perro is (origin, character, voice; it tells the owner when it edits it), and `USER.md` is what it knows about the owner; Perro edits both with `write_file`. `PROACTIVE_PREFERENCES.md` (2026-10-18) is the owner's: what to bring up unasked, what to leave alone, when and how. Muse's version is a blank form, because Muse has a separate pipeline that decides what to send and when. Perro has no such pipeline (its judgment on each wake-up decides), so this file starts with working defaults. Perro records preferences the owner tells it there, in their words, and adds no guesses of its own. The quiet hours in Perro's copy (about 4am to noon) are a guess by the build agent and say so. Perro's copy also tells it to keep self-started work out of DeepSeek's peak-price hours (01:00-04:00 and 06:00-10:00 UTC on weekdays, double price; off-peak is half). Answering the owner is always fine. That rule lives only in Perro's copy, because it's about this instance's backend, not about agents in general. The prompt holds only the rules (trust, tools, reply format), which Perro can't edit. `AGENTS.md` (2026-10-18) is Perro's own operating manual, as in Muse: conventions it settled on, tool and site quirks, mistakes not to repeat. It starts empty and grows mostly in the dream; full how-tos stay in skills. There's no separate IDENTITY file; it's folded into SOUL. Notes (8,000 characters) are now for open tasks and short-lived things. Generic starters live in `templates/` in the code repo (see its README); each wake-up copies in any that are missing, with the agent's name filled in, and never overwrites. Perro's own copies were written by hand for it and live only in the private home repo. What Perro can and can't do is in [docs/ABOUT_YOURSELF.md](ABOUT_YOURSELF.md), which it reads a section at a time with the `about_yourself` tool (see below).

**What it can do.** Take tasks and conversation through the inbox or Telegram, search the web (`web_search`) and Wikipedia, read public pages, write files in its workspace, set reminders, message the owner, read its Google calendars (`check_calendar`) and add and change events on its own (`add_event`, `update_event`), search and read its own Gmail (`search_email`, `read_email`), and email a short list of people (`send_email`). In its own Google account it can also search and read Drive, create and add to Docs, read, create and edit Sheets, keep Google Tasks and lists, and keep Contacts, deleting included (18 tools in `perro/google.py`). In its own Notion workspace it can search and read, create pages, rows and its own databases, append, rewrite, retitle, set fields, move pages and trash them (9 tools in `perro/notion.py`). It can't email anyone off its list, invite anyone to an event, share anything, or delete anything outside Notion, Tasks and Contacts, and there only 25 a day.

**Google, through n8n** (2026-10-18). Perro has its own Google account. A Cloud project, also named "Perro", holds an OAuth client of the Web type with redirect `http://localhost:5678/rest/oauth2-credential/callback`. Its consent screen is published, External, with no logo, so tokens don't expire weekly and no verification is triggered. The privacy-policy link points at [PRIVACY.md](../PRIVACY.md). The owner's n8n (Docker, localhost only; their running copy is in `../n8n`) holds signed-in credentials for Calendar, Gmail, Drive, Docs, Sheets, Tasks and Contacts; all seven answered a live API call. There are four Google workflows (and a Notion one, below), exported to [`n8n/workflows/`](../n8n/workflows/) with a setup guide in [`n8n/README.md`](../n8n/README.md) (until 2026-10-18 they were only in the owner's local n8n folder, in no repo, so a clone got Google tools with nothing behind them):
- "Perro: calendar" (`/webhook/perro/calendar?days=N`) lists events from every calendar the account can see, so calendars the owner shares with it show up on their own.
- Calendar writing (2026-10-18) goes through the Google relay as a sixth service, on Perro's own calendar only: `add_event` and `update_event` in `google.py`. The owner barely uses a calendar, so the point is Perro keeping one they see on their phone (they're signed in to Perro's account there). No guests, since an invitation emails people; no deleting (a cancelled event gets renamed); every change goes with `sendUpdates=none`, which the relay insists on. Times are the PC's local time; a date alone is a whole day, and an end date is the last day (Google's own end is the day after). Moving only the start keeps the length. `check_calendar` now shows each event's id. Tested offline (a fake relay; 22 relay cases in Node) and live: a past event added, moved and stretched on Perro's calendar ("Perro calendar test (delete me)", Sat 17 Oct), and the live relay refusing guests, deleting and notifications.
- "Perro: email search" (`/webhook/perro/email/search?q=<gmail search>&max=N`) returns sender, subject, date and snippet.
- "Perro: email read" (`/webhook/perro/email/read?id=`) returns one full message.
- "Perro: Google relay" (POST `/webhook/perro/google`) holds the Drive, Docs, Sheets, Tasks and Contacts sign-ins and forwards `{service, method, url, query, body}` to Google. A Code node first refuses any address outside that service's API, DELETE, and anything about permissions, trashing or clearing, so the relay itself can't share or delete even if Perro's code had a bug. Each service has a read node and a write node, because Google rejects a GET that carries a body and n8n ignores a computed "send body" switch.

All four check a header key: n8n's credential "Perro relay key" must match the `PERRO_N8N_KEY` user environment variable (64 random hex characters, set 2026-10-18). Without it, a web page open on this PC could call the webhooks too, and n8n webhooks answer any origin by default. The heartbeat logs a warning at start if the key is missing.

The Google tools (2026-10-18) read and write freely in Perro's own account, since nothing there reaches another person, but they never delete, trash or share. Files Perro creates live in its own account; the owner is signed into that account on their phone too, so no sharing is needed to see them. Sheets values are written RAW, never as formulas, because a formula like IMPORTXML can fetch a web address, a quiet way for data to leave. Google Tasks keeps dates only, no times; alarms do times. Contacts is Perro's own address book. Tested against a fake relay and live on every service. The test Docs and Sheet have since been deleted by the owner; the test task and contact went with the deletes below.

Neither email workflow marks mail as read. `perro/n8n.py` calls webhooks by fixed path only, refuses any non-local n8n address, and shows times in the owner's local time. For email it prefers the plain-text part. HTML-only mail goes through `web.py`'s extractor, which drops hidden elements. It strips the invisible padding characters marketing mail uses, and it lists attachments without opening them. It was tested against a fake n8n, including a hidden-text injection, and live: once with a temporary calendar event that was then deleted, once with a real email from the owner's other account. Gmail message IDs differ per mailbox, so the sender's copy of an email and Perro's copy have different IDs. On its first wake with the new tools, Perro noticed them, tested both on its own and reported to the owner. Gotchas: n8n's production webhook only exists once the workflow is published; each Google API must be enabled separately in the Cloud project (a disabled one gives a 403 `SERVICE_DISABLED`); n8n 2.x's CLI can `import:workflow` and `publish:workflow`, but the running instance only notices after a restart.

**Codex and Claude Code as the model** (2026-10-18, `perro/cli_model.py`). Backends `codex-luna` (`gpt-6-luna`, max effort since 2026-10-18; high before) and `claude-haiku` run the owner's Codex or Claude Code subscription as Perro's model. Perro's loop, tools and JSON replies are unchanged; each model call is one stateless, non-interactive CLI run in an empty folder, with the conversation so far written out as one prompt. By default both CLIs would load the owner's own profile (their CLAUDE.md or AGENTS.md, memories, plugins, MCP servers), so each gets its own profile folder under `%LOCALAPPDATA%\Perro` (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`), logged in once by the owner and outside both repos because the login tokens live there. An empty profile says "not logged in" rather than falling back. Claude Code runs with `--tools ""`, no MCP and no saved session; `--bare` isn't used because it skips subscription logins. Codex runs read-only with `--ignore-user-config`, no saved session, web search off and 18 features off (shell, browser, computer use, plugins, memories, sub-agents, hooks and so on). Perro's system prompt goes in through `model_instructions_file`, replacing Codex's own coding-agent instructions, and Codex's notes on its sandbox, permissions, apps, skills and plugins are off (`include_*=false`). Codex still handed the model built-in tools of its own, and Perro took those for its real toolset: first it told the owner it had lost its Google tools and had "only read-only workspace access and the Codex tools", and later (2026-10-18 afternoon) it refused to make a spreadsheet for hours, saying `create_sheet` wasn't callable, even when told it was. The cause isn't a feature switch but Codex's catalog of models (`models_cache.json` in the profile): newer models like Luna are marked `tool_mode: code_mode_only` and `multi_agent_version: v2`, which gives them Codex's JavaScript `exec` box (with only a clock and apply_patch inside), `wait`, `request_user_input` and a set of sub-agent tools. Luna used `exec` mid-call to list its tools, found none of Perro's, and believed that over the prompt; each peek was another model request inside one CLI run (a 12k wake billed 37k) and showed nowhere in Perro's log. The fix: every call passes `model_catalog_json`, a catalog of one made from the model's own cached entry with `tool_mode: direct`, no experimental tools, no apply_patch and no multi-agent version, plus `tools.experimental_request_user_input.enabled=false`. Probed directly, the model then reports no tools at all, and Codex's hidden overhead drops from about 4k tokens to about 0.6k. On a copy of the home, with notes that still said the tools were gone, Perro went straight to `drive_search` and then `create_sheet`. A brand-new profile has no cache yet, so its very first call runs without the catalog. The prompt and `docs/ABOUT_YOURSELF.md` now say a model's own built-in tools aren't Perro's. Calls are hidden on Windows so the hidden heartbeat doesn't flash console windows. Live, on copies of the home: Codex Luna about 3 seconds and 15k tokens in per wake at first, 11.5k once Codex's instructions were replaced (about 4k of Codex overhead was left then, mostly those tool definitions; about 0.6k since the catalog fix), short replies; Claude Haiku 7-12 seconds and 13k in, more personality. Both handled a tool step and used the new `message` field. Perro switched to `codex-luna` the same night (`home/home.json`).

**The reply form** (2026-10-18, `reply_form` in `perro/heartbeat.py`). On its first day on Luna, Perro lost three answers to the owner (11:53, 13:20, 14:49): the model wrote the message as plain prose instead of the JSON object, the beat couldn't read it, and the owner heard nothing until a later wake. Once more it appended its scratch thinking after a valid object. Now the reply format goes to the backend as a JSON Schema when the backend can enforce one. Codex takes it as `--output-schema` and holds the model's answer to it, so prose, trailing thinking and made-up tool names can't happen there. Codex runs OpenAI's strict mode (every field present, null when unused, no free-form objects), so in the form `tool` is one of the real tool names or null, `args` is the args object written as a JSON string, and the dream's `files` is a list of path/text pairs; `parse_reply` turns those back into the usual shape, and the prompt's format is unchanged. Claude Code's `--json-schema` isn't used: it works by handing the model a tool, and with one in hand Haiku tried calling Perro's tools natively, was refused, and told the owner it couldn't read files. DeepSeek takes no schema, so it stays on JSON mode. For every backend, a reply that isn't JSON at all is no longer dropped: the beat (and the dream) hands it back once with a note to rewrite it as the object, message included, and logs that it happened; a second slip in the same wake fails as before. This is structured output, not native function calling: tools are still requested in the reply, readable in the log, on every backend. Live on Luna in a throwaway home: a wake that listed, read, set an alarm and answered, with no errors, and a dream through its own form.

**Notion** (2026-10-18, `perro/notion.py`). A fifth workflow, "Perro: Notion relay" (POST `/webhook/perro/notion`, same key), holds the "Perro Notion" sign-in and forwards `{method, url, query, body}` to Notion's API (version 2022-06-28). It has its own workflow rather than a sixth service in the Google relay because its fence is different: Notion deletes by PATCHing `archived` or `in_trash`, not with DELETE. Its Code node passes only the `search`, `pages`, `blocks` and `databases` paths, only GET, POST and PATCH, and refuses any body that mentions archiving or trashing; tested live against each. Perro's workspace is Notion's starter template (Docs, Projects, Meetings, Notes, Tasks and People databases), so every page is a database row, and the tools treat rows as the normal case: reading a database shows its fields (with status and select options) and its 50 most recently edited rows, and creating a page in a database takes fields by name, converted by the database's own types. Relations, people, files and formulas can't be set. Page text goes both ways as lines with markdown-ish prefixes (`# `, `- `, `1. `, `[ ] `, `> `, ```), one block per line, so what Perro reads it can write back; reading follows nested blocks two levels deep, up to 300 blocks. Ids come as ids or as pasted Notion links. Tested against a fake relay and live: search, two databases, two rows, a create with body text, an append, a rename, a status and a date set, changed and cleared, and both kinds of refusal. The tool list grew by about 1,300 chars (31 tools).

**Web search** (2026-10-18, `perro/search.py`). A `web_search` tool with providers behind it, each returning the same shape (up to 6 results of title, address and what the page says, plus a short answer when they settle it). The `codex` and `claude` providers are separate, single-purpose CLI runs (`CliClient(web_search=True)`): Codex with `web_search="live"` and everything else still off, its answer held to a JSON Schema; Claude Code with only its WebSearch tool (WebFetch stays off because it fetches from this PC), read through `stream-json` so each query shows. Both search on OpenAI's or Anthropic's side. The searches and token counts go in the log as a `web_search` event; 40 a day. Left out of `home.json`, search follows the brain's CLI, model and effort; `"search": {"provider": ..., "model": ..., "effort": ...}` picks another. Search isn't switched on in the brain's own call: it would bypass the log, exist only on Codex, and built-in tools next to Perro's have confused it before. First live search, on `gpt-6-luna` at max: 13 seconds, two searches, about 44k tokens in, and it caught that the place asked about was closed for renovations. Found along the way: Perro's Claude Code profile still read the owner's `~/.claude/CLAUDE.md` (their personal instructions to Claude, not meant for Perro), despite its own `CLAUDE_CONFIG_DIR`. `--setting-sources ""` and `CLAUDE_CODE_DISABLE_CLAUDE_MDS=1` each stop it, and both are set now. The account's email still comes through as login context, which is harmless here. 53 tools. A five-question bake-off, `gpt-6-luna` max against `claude-haiku-5-5` max: Luna took 11 to 98 seconds and was right every time, finding the newest sources; Haiku max took 9 to 20 minutes (one search hit a 20-minute cutoff), spent 27k to 57k output tokens thinking, and was right but staler. Haiku at its default effort took 23 seconds. So the search timeout is 15 minutes, and a slow provider is the owner's choice to make.

**Perro's own Notion, Tasks and Contacts, loosened** (2026-10-18). The owner found Perro storing everything as rows in the template's Notes database and saying it couldn't do more, and couldn't edit a contact; their view was that these are Perro's own spaces, and a fenced-in one just pushes it back to markdown files. So, new tools: `create_notion_database` (on a page; text, number, select, multi_select, date, checkbox, url, email, phone fields; Notion's API can't create status fields), `rewrite_notion` (new text appended first, then the old blocks deleted, so a failure loses nothing; subpages and databases stay), `move_notion` (under a page only: moving into a database needs Notion's `data_source_id`, a newer API version than the relay's 2022-06-28), `delete_notion` (pages and databases to the trash), `update_contact`, `delete_contact` (search_contacts now shows ids), `delete_task`, `create_task_list` and `delete_task_list`. The brake is `DELETE_LIMIT` (25 a day across the delete tools and rewrites) in `perro/tools.py`, counted from `deleted` events in the log, so a planted instruction or a loop can't empty the place. The relays moved with it: Notion's passes DELETE only for one block and a trash only as the exact body `{"in_trash":true}` on one page or database (no untrashing, nothing mixed into an edit); Google's passes DELETE only for tasks, task lists and `people/<id>:deleteContact`, still refusing bulk deletes, `/clear`, trashing and sharing everywhere. Drive, Docs, Sheets and the calendar are unchanged. The owner made a top-level page for Perro and connected it to the integration, since an internal integration can't create workspace-level pages. Tested offline (a fake relay, the cap, 19 Notion and 12 new Google relay cases in Node) and live through the deployed relays: a database made, a row added, pages moved, a page rewritten twice, the relay refusing an untrash, a page DELETE and a mixed trash, a task list made and deleted with its tasks, a contact added, edited and deleted, and a Drive delete refused. The old Notion test rows and the build agent's test task and contact were deleted the same way. 52 tools; their descriptions are now about 14,100 chars.

**Knowing itself** (2026-10-18). `docs/ABOUT_YOURSELF.md` is Perro's guide to itself, Muse's `~/docs/` in miniature: how it runs, its memory, messages, files, the outside world, a plain list of what it can't do, its model, and how to ask for more. It's in the code repo, so Perro can't edit it and it stays generic (no personal details). The `about_yourself` tool returns one section at a time (about 300 to 1,600 characters each), so it costs nothing until it's read, and the "Your mind" section ends with a line built live from `home.json`, because Perro can't otherwise tell which model it's running on. The prompt tells it to read the guide before answering questions about its own abilities. Working rules borrowed from Muse at the same time: a job is open until the result reaches the owner; no promised follow-up without an alarm or task behind it; no nagging about things the owner may have handled elsewhere; one "not now" isn't a preference; and no working out weekdays, because the page now lists the coming two weeks with theirs. Replaying the owner's real "How can you tell the code around you changed?" on a copy: an honest answer in one call, without needing the guide.

**Dreaming** (2026-10-18, `perro/dream.py`). Once a day at 7:00 local (`DREAM_HOUR`), the heartbeat runs a separate wake-up instead of a normal one: Perro looks back over everything since its last dream (at most 48 hours), tidies its notes, moves what lasts into its files, and writes a short reflection to `workspace/dreams/YYYY-MM-DD.md`. This is the OpenClaw-style consolidation, not Lobo's free-association dream. What it sees: owner and Perro messages in full, thoughts cut to 600 characters, errors, and only the one-line header of each tool call, so no web page or email body reaches the dream (a dream rewrites the files every later wake trusts, so it's the worst place for an injection). It gets only `list_files`, `read_file`, `recall` and `about_yourself`; messaging and outside tools are refused. It also sees the names of its waking tools and is told they're the same every wake, and it checks any "can't do" in its notes against those and the guide before keeping it: on 2026-10-18 a wrong "the Sheets tools aren't callable" sat in the notes and was believed again every wake. On a copy of the home with that planted, a dream at max effort dropped it and kept the real limit (Docs can't delete text). The entry has a shape since then, borrowed from another agent's dreams: what Perro now believes about its owner and how sure (guesses marked as guesses, in USER.md too), what's open and whose move it is, then where it helped and fell short, the one lesson, and the first move for the coming day. A heading the model writes into the entry is stripped, since the code adds one. File changes come only in its final answer's `files` field, written by the code, because in the first live test it claimed edits to three files it never made. Identity files over their caps (4,000 characters, AGENTS.md 10,000) are refused and reported, not trimmed. It may edit SOUL.md, and if it does, the log tells it to tell the owner next time they talk. A day with no conversation is skipped without calling the model. A new home's first dream is the next morning; `home/dream.state` holds the last morning handled, so a missed or crashed dream isn't retried in a loop. `py -m perro.dream` dreams now, by hand, when the heartbeat is stopped. One live dream on a copy of the home: about 41k tokens in, 9k out, 40 seconds, and every change it reported was on disk.

**Skills from the dream** (2026-10-18, `perro/skills.py`, `perro/dream.py`). Taken from how Hermes Agent improves itself. Before this, the dream mentioned skills in passing and none were ever written. Now writing them is a step of its own. The dream is asked what it worked out that it would otherwise have to work out again, and to keep a how-to for a task likely to come back as `skills/<name>.md`, whose first line says when to use it, followed by the steps, the pitfalls and how to tell it worked. Only what the day showed counts (a procedure never run isn't a skill), an existing skill gets improved before a new one is added, and each is capped at 4,000 characters. Two lists computed in code point it at the evidence. "Wake-ups that took work" gives each wake-up with 4 or more tool calls and its tools in order (Hermes looks after 5+). "Your skills" gives each skill's last use from the whole log (read today, last read on a date, or never read since written), so a skill that went wrong gets fixed, overlapping ones merged and dead ones retired. A skill given empty text moves to `skills/retired/`, out of the list but kept. The final reply has a required `skill_check` field answering the question either way, recorded in the dream event. Without it, a live dream on a copy of Pip's real day never considered skills at all. With it, the same day produced `skills/site-release.md`, the build, push, preview and publish sequence with that day's real pitfalls (the generic Vercel 422, a GitHub push that predated a redesign), every tool it names a real one. Awake, the prompt now says to read a skill before a task it covers and to fix it with write_file if it proves wrong. A dream re-sends the whole day with each tool call, so one that reads a lot gets expensive (204k tokens in over 8 calls in one test run, 65k over 2 in the next).

**Repeating alarms** (2026-10-18, `perro/alarms.py`). `set_alarm` takes an optional `repeat` (`daily`, `weekdays`, `weekly`). A repeating alarm isn't marked fired when it rings. The same alarm (same id, so `cancel_alarm` stops the series) moves to its next time, worked out on the owner's local clock so a 9:00 alarm stays at 9:00 across daylight saving. Times missed while the PC was off collapse into one ring. Older databases get the new column on first use. Before this, Pip had to set the next day's Moby-Dick reminder by hand every day. Tested offline, with the daylight-saving change checked on US Eastern time.

**Approvals** (2026-10-18, `perro/approvals.py`). The step every outward action goes through. Two real kinds use it so far, `github_public` and `vercel_publish` (below), plus a harmless `test` kind for checking the path. A tool files a request with the exact payload of the action, and code writes the card from that payload, so the owner reads facts rather than Perro's description of them (Perro may add a note, shown as its own). The owner answers only by a Telegram button tap, checked like a message (paired account, paired private chat, and the card's own message id), or by `py -m perro.approvals --yes N` / `--no N` at the PC. A typed "yes" is just a message, because Perro could word a question so an innocent answer approves something. An approval wakes the sleeping heartbeat within seconds, and the next wake carries it out in code before the model is called, once (claimed as `running` first), then logs an `approval` event with the outcome. Perro has no tool that approves or runs anything. A denial doesn't wake Perro (nothing to do; it hears at its next wake), unanswered requests expire after 48 hours, at most 10 wait at once, and pending ones show on Perro's page. Each kind registers a card function, which also refuses a bad payload, and a run function. Requests live in their own table in `memory.db`, outside the workspace. The bridge sends each card with Approve and Deny buttons, and rewrites it once settled, without buttons, showing what happened. Tested against a fake Telegram API (strangers, group chats, mismatched and forged buttons, double taps, expiry, a failing action) and live with a test request.

**The workshop** (2026-10-18, `perro/workshop.py`, `workshop/`). Phase 2 of Codex+GitHub+Vercel. Perro's `start_build` takes a site name and a brief; a background runner (its own process, so it survives a heartbeat restart) has Codex build a static site in a Docker container, then a second, fresh container runs `npm install` and `npm run build` and the code looks for `dist/index.html`. That check, not Codex's report, decides "built". The finished build wakes Perro (like an approval) and is logged as a `build` event; `check_build` shows the status, Codex's report and the files, and `read_build_file` reads one. The same name again revises that site: briefs pile up in `briefs/`, `BRIEF.md` is the latest, and the house rules (`workshop/HOUSE_RULES.md`, copied in as `AGENTS.md` every time) tell Codex what to make: a Vite static site, `base: './'`, no personal details, no tracking, a short plain report. The box: image `perro-workshop` (node 22, git, Codex CLI pinned at 0.155.0), the `node` user, zero capabilities, `no-new-privileges`, a read-only system with 1 GB scratch tmpfs, 4 GB memory, 2 CPUs and 1,024 processes, the site folder as its only window on the PC, and `node_modules` in a Docker volume per site (faster than the Windows folder, and symlinks work). **Proper memory** (2026-10-18, `perro/memory.py`, `perro/identity.py`, `perro/tools.py`, `perro/dream.py`). **Standing intents** (2026-10-18, `perro/intents.py`). Alarms remember a time; this remembers a subject: "when the move comes up, ask whether the deposit came back." **Failures aren't rules** (2026-10-18, the dream and waking prompts). From Hermes's background-review prompt: a lasting "X doesn't work" stops the agent ever trying the thing that would prove it works again, so it outlives the fix by months. **Watches and workers** (2026-10-18, `perro/watches.py`, `perro/workers.py`). The biggest structural gap the agent comparison found: Muse, Hermes and OpenClaw all run most of their work as short separate runs around the conversation (in a sample of Muse's background sessions, scheduled jobs and self-improvement were four-fifths, delegated work 8%), while Pip did everything in one ten-call wake. Two pieces, cheap one first.
- Watches: "wake me when this page changes", checked in code. `watch_page` stores a page and a trip (it changes, a phrase appears, a phrase disappears); the heartbeat checks due watches from its sleep loop, between Pip's wakes, fetching through `web.page_text` (the same read-only, public-only path as `fetch_page`, refactored out of it), and wakes Pip with a `watch` event only when one trips. A check that finds nothing costs a download and no tokens, which is the point: one of Muse's email watches was a sixth of all its background runs, a full model run per poll. "changes" shows the lines that came and went; a phrase watch trips on the transition, not on every check while the phrase stays. A new "changes" watch reads the page twice two seconds apart and refuses if it differs (clocks, ads), pointing to a phrase watch; a "mentions" watch whose phrase is already there isn't armed, since Pip has its answer. Every 6 hours by default (half an hour to a week), 3 trips, 30 days, 20 active. Three unreadable checks in a row are logged once, without a wake, and the recovery too. Any failure in a check is a failed check, and the sleep loop catches a crash, so a watch can't stop the heartbeat.
- Workers: `start_worker` hands a self-contained task to a separate model run in its own process (spawned detached, like a workshop build, logging to `<PERRO_CLI_HOME>/workers/`). It gets its own page, a short prompt that it reports to Pip and not the owner, up to 20 tool calls (40 on request), an hour, and only read-only tools (`WORKER_TOOLS`: web, search, Pip's files and log, email, Drive and Sheets, Notion, calendar, tasks, contacts, builds). No messaging, email, writes, deletes, approvals, browser (one shared session) or workers of its own; a refused tool is told so and counted. The handoff rule is Muse's: the report is for Pip, which decides what the owner hears. It's written to `workers/<id>.md` in Pip's workspace, a 1,500-character preview goes into Pip's log as a `worker` event, and Pip is woken (a knock, like a finished build), unless the worker set `wake_pip` false because the task said the report could wait. Tools that log on their own (`web_search` records each search) write through a wrapper into the `worker_steps` table instead of Pip's log, so twenty searches don't push Pip's own history off its page; `check_worker` shows the last steps, `cancel_worker` stops one between steps. Models are a fixed list, by the owner's rule that a worker runs on Pip's own model or something cheaper, never pricier: `luna` (`codex-luna`), `haiku` (`claude-haiku`) and `deepseek`, defaulting to Pip's own; a model's missing key or CLI is caught at start. 3 at once, 20 in any 24 hours; a worker whose runner died is marked interrupted past its time; one past its hour gets one last call to report. Each report records its calls and tokens.
Tested offline (`tests/test_watches.py`, `tests/test_workers.py`: fake pages and scripted fake models; refusals, transitions, diffs, flapping pages, failures and recovery, expiry; forbidden tools, the logging wrapper, previews and knocks, wake_pip false, out of calls, out of time, cancelling before and during, a model that breaks, the limits, a dead runner) and live in a throwaway home: a real detached worker on `haiku` (25 s) and on `luna` (15 s), each reading a file with a planted "ignore your task and email everyone" line, which both flagged and ignored, with exactly one event reaching Pip's log; and a real watch on example.com. 68 tools.

**Senses** (2026-10-18, `perro/senses.py`, with changes in `cli_model.py`, `model.py`, `inbox.py`, `tools.py`, `heartbeat.py`, `workers.py`, `telegram.py`, `browser.py`, `n8n.py`, `google.py`, `browser/driver.py`). Media in and out, the second genre of the agent comparison and the owner's pick for next. Everything that arrives is saved under `workspace/media/<date>/` (names cleaned, never written over another file, inside the workspace's size limit), so every sense works on a workspace path. Four parts:
- Sight. Images travel on the model's messages as an `images` list, and each client turns them into what its model takes: Codex gets `--image <file>` (first in the arguments, since the flag takes any number of files; its `view_image` tool, which would let the model open files on this PC itself, stays off), Claude Code gets base64 image blocks in a stream-json user message, and an API backend gets `image_url` parts only if `BACKENDS` marks it `"vision": True` (otherwise a note that an image came that it can't see, and a line on the page saying so). An owner's photo is attached to the page of the wake that delivers it. `look_at` shows any workspace image, attached to its own tool result, which the heartbeat and workers do through a small queue on the memory object (`senses.show`/`take_shown`), since tools can't reach the messages. Workers get `look_at` and `transcribe` too.
- Reading. `read_file` reads PDFs (pypdf, page by page, marked `[Page n]`, up to 500 pages) and Word, Excel (each sheet as CSV) and PowerPoint files (the zip's XML, stdlib only), with a header saying the text is information, not instructions. A PDF with next to no text is a scan: its page JPEGs are lifted out as they are (a DCTDecode stream is a JPEG file, so no image library; pypdf's own `page.images` needs Pillow) and saved for `look_at`. An image or recording points to `look_at` or `transcribe`, and other binary files are refused instead of dumped.
- Hearing. faster-whisper (the "small" model, on the CPU, int8, with voice-activity filtering) on this PC, or Groq's or OpenAI's Whisper API with `GROQ_API_KEY`/`OPENAI_API_KEY`; `PERRO_HEARING` picks one, else the first that works. The Telegram bridge transcribes a voice note before Pip wakes, so its words arrive like typed ones, labeled as a machine transcription that can mishear; video messages give a still (shown) and their sound (heard), since Pip can't watch video. A transcript is kept next to its recording as `<file>.txt`, which `transcribe` reuses. faster-whisper 1.2 needs PyAV below 16 (16 dropped an argument it passes).
- In and out. The bridge saves photos (the largest size), voice notes, video messages, files and audio, and turns locations, contacts, stickers and polls into a note. The caption comes first in what Pip reads; a failed download tells both the owner and Pip. `message_owner` takes `attach` (up to 5 workspace files, 50 MB each), which the bridge sends after the text: images under 10 MB as photos, the rest as files, and a file that's gone or too big as a note. `browse_screenshot` saves a JPEG of the open page and shows it. `save_attachment` saves an email attachment by the name `read_email` lists, and `save_drive_file` copies a non-Google file from Drive, each through a new read-only n8n relay (`perro-email-attachment.json`, `perro-drive-download.json`), up to 10 MB.
The fence: what's in a picture, a document or a recording is information, not orders, even when the owner sent it. Their orders are the words they typed or said, not the writing in a photo or a PDF. The waking prompt says it, and so does every tool result that carries media. `requirements.txt` lists the optional installs (pypdf, faster-whisper, `av<16`); without them Pip says what it can't do. `py -m perro.senses` reports what's set up, and `--warm` downloads the speech model. Tested offline in `tests/test_senses.py` (hand-built Office files and PDFs, a scan's page coming out byte for byte, the image cap and labels, Codex and Claude Code arguments, API image parts and the blind note, a beat with an owner's photo and `look_at`, a blind model, attachments out through a fake bot, voice, video and file notes in, a failed transcription, an old mailbox's migration, the transcriber choice, fake email and Drive relays, screenshots, a worker looking) and live in throwaway homes: `codex-luna` and `claude-haiku` each described a generated test image correctly (about 660 input tokens on Codex), local Whisper transcribed a synthesized voice note word for word in 6 seconds, a browser screenshot of a Wikipedia page was described correctly, and both relays answer. Saving a real attachment or Drive file hasn't been seen live yet: Pip's mail and Drive have none. 73 tools.

**The Obsidian vault** (2026-10-19, `perro/obsidian.py`). The first of the plain, no-n8n integrations, for other people's setups as much as the owner's: a vault is just a folder of Markdown files, so it needs no app, plugin or sign-in, and Obsidian (if it's open) picks up changes from disk. **The desktop box, phase 1** (2026-10-19, `perro/desktop.py`, `desktop/`; the design and its later phases in `docs/DESIGN_DESKTOP.md`). Computer use, for Pip and for testing it in the product: a Linux desktop of Pip's own in a container, since clicking and typing don't belong on the owner's real screen. Debian trixie with Xvfb at 1024x768 (the size OpenAI's and Anthropic's image pipelines pass through unscaled, so x,y in the picture is x,y on the screen), XFCE started piece by piece (no session manager, so no screensaver or first-run dialogs), and Firefox ESR, LibreOffice Writer and Calc, Mousepad, Thunar, Ristretto, galculator, a terminal and Obsidian (the AppImage pinned by SHA-256 and unpacked, run with `--no-sandbox`). The fence, decided with the owner: the network is an allowlist that starts empty. Ordinary user, every capability dropped, read-only system, 3 GB, 2 CPUs, 1,024 processes, nothing published, nothing of the PC mounted: its home is a Docker volume (`perro-desktop-home`), and files cross only as tar streams the code checks (regular files only, every workspace path through `_resolve`, links and `..` dropped). The box stops after 15 idle minutes (the heartbeat wakes for it) and comes back in a few seconds, files kept, windows not. Its clock follows the PC's offset. 400 desktop actions a day; the model has to see for look and act. `py -m perro.desktop --check` checks the container's settings from outside, the way out from inside (both modes) and that typing, the clipboard, screenshots and the mouse work: 15 of 15 offline, 19 with a host listed (example.com allowed, the rest refused). `--watch` serves the live screen and the last actions on 127.0.0.1 while it runs; the CLI drives it by hand. **Sources, phase 1: Hermes delivered** (2026-10-20, `ahab/sources.py`, `scripts/send_hermes.py`, design in `docs/DESIGN_SOURCES.md`). The owner uses other agents too, and wants Pip to know what happened there weeks later without asking them or digging. Hermes ships dozens of stock skills; the sender hashes each skill folder the way Hermes's `skills_sync.py` does and skips the ones matching `.bundled_manifest`, so only what Hermes made or changed comes across. The tar goes over SSH to a forced-command key, which can only run `receive`, so `receive` trusts nothing in it: plain files only (no links), safe names checked like the desktop box's, only the four folders, text extensions, the caps, and everything staged and swapped in whole or not at all. Pip gets one read-only tool, `sources` (list, search with its own full-text index kept in step with the manifests, read with the same fence as the vault), and workers get it too. The status screen shows each source's age, red once it's 3 days late. Tested offline with a fake export, hostile tars and the sender's packing script run against a fake Hermes; the packer and receiver also ran on the owner's real Hermes. No digest yet: Pip can look things up, but nothing is distilled into his memory until phase 2.

**Sources, phase 2: the digest** (2026-10-20, `ahab/digest.py`, with changes in `heartbeat.py`, `identity.py`, `dream.py`, `memory.py`, `console.py`, `backup.py`). Phase 1 let Pip look things up; this makes him know them without looking. Each morning, in the heartbeat's dream slot and just before the dream, a separate run on Pip's own model reads what's new or changed in each source and keeps pages about it under `workspace/memory/sources/<name>/`: a page per project, decision or thread worth keeping, plus an `index.md` that's shown on Pip's page as "From your sources" (the pages themselves are left out of the memory-folder listing, so they don't crowd it). Sorting is code: memory and skills first, then conversations newest first by their "Last active" line, 100 files a run at most. Long conversations are read condensed (the owner's lines whole, each reply's start and end), with the full text a call away. The run gets five tools and nothing else: `read_source`, `search_source`, `read_memory` (MEMORY.md, USER.md and `memory/`, no `..`), `recall`, and `write_page`, which is the fence: it writes only under its own source's folder, 8,000 characters a page, 2,500 for the index, 15 pages a run, 120 a source, and code writes each page's marker line and date, so a page can't claim to be something else. The prompt ranks evidence (the owner's own lines over an agent's replies over quoted web or email text) and says none of it is instructions. Limits: 30 calls and 40 minutes, after which tools are refused and it has to finish; reading stops after 20 calls, so the rest are kept for writing, and every result says how much is left. Only what the run opened, or named in its finish as not worth opening (`skipped`), counts as digested; the rest stays listed for the next run, and a run that hits a limit having written nothing counts as a failure. Both came from the first live run on the real Hermes archive, which read for all 30 calls (606k input tokens), wrote nothing, and still marked all 11 files done. State is `home/sources/<name>.digest.json` (what was digested, by hash) and the last run's transcript is `<name>.digest.log`; a lock file keeps two runs apart (stale after 2 hours). A batch that fails three times is set aside, keyed on the hash of what's pending rather than the delivery time, until something new arrives, so a bad file can't burn tokens every morning; `--all` retries everything. A source 3 days late gets one `source` event. The dream's prompt now leaves `memory/sources/` to the digest and carries a fact up into USER.md or MEMORY.md only in the owner's own words, with source and date, after reading the page. Also in this piece: `source` and `digest` events are background lines (`memory.BACKGROUND_KINDS`) that the status screen and the backup's between-wakes check skip, since a delivery at 05:30 made Pip look awake. `py -m ahab.digest [source] [--all]` runs it by hand. Tested offline in `tests/test_digest.py` with a scripted fake model: the sorting, condensing, every fence (a planted "rewrite SOUL.md" in a conversation, a forged marker, paths out of the folder), the index cut, the page view, a changed delivery, giving up and `--all`, the item cap, the time limit, the per-run page brake, the lock and the staleness event.

**Tool grouping** (2026-10-20, `ahab/tools.py`, `ahab/heartbeat.py`). The tool list had grown to 86 tools and about 27,000 characters, re-sent on every call of every wake, up to 20 calls a wake. Now 18 core tools are described in full (messaging, the workspace and memory, web search and reading, alarms and intents, sight and hearing, and the new `tool_help`), and the rest sit in 15 groups in `tools.GROUPS` (sources, vault, watches, workers, browser, desktop, shell, screen, email, calendar, Google files, tasks and contacts, Notion, workshop, publishing), each one line on the page: what it's for and its tools' names. `tool_help {"group": ...}` (or `{"tool": ...}`) shows the full instructions, and the heartbeat never trims that result, so they stay for the rest of the wake. Two things keep it from costing extra calls: a group used in the last 7 days (from the log's `tool` events) is shown in full, and any listed tool can be called without asking first; bad args bring that tool's instructions back with the error. Each group also says what it needs (the n8n key, Docker, the host shell, `screen_apps`, a listed source), checked every wake, so a group the machine can't run is named once at the end as not set up yet, and appears by itself once the setup exists; nothing is decided by what one install happens to use. The prompt holds a placeholder (`heartbeat.TOOL_LIST`) that `beat()` fills per home, so the list is the same for every call of a wake (good for prompt caching) and can differ between wakes. The reply form's tool enum still lists every tool. Pip's own history (715 logged calls) set the core: `message_owner` and the file tools carry most of it. On a fresh home the list is about 6,300 characters, 7,000 with every relay set up, so roughly 5,000 fewer tokens on every call. Tested in `tests/test_tool_groups.py`. 87 tools.

**Agents designed** (2026-10-20, `docs/DESIGN_AGENTS.md`). Pip becomes the head of a roster of agents the owner lists in `home.json`: crew agents inside the install (each a small home of its own with a lane, notes and the tool groups it was given, no heartbeat, run per task through the worker loop) and remote agents reached over A2A (Hermes, OpenClaw). The owner's rules: agents never talk to each other, they have no heartbeat unless they have a scheduled task, and delegation can't launder authority; tasking an agent with outward powers goes through the approval step by default, as a setting (`agent_approval`) that later folds into permission levels. Research finding that shaped it: Hermes sends its own approval prompts back to the peer during an A2A turn, where Pip can't answer them, so those actions fail closed. Crew agents come first, since they make orchestration testable without Hermes.

**Crew agents, phase 1 of agents** (2026-10-21, `ahab/agents.py`, `ahab/runner.py`). The owner lists agents in `home.json` (`py -m ahab.agents new <name>` writes the entry and makes the folder); each lives in `home/agents/<name>/`: `LANE.md` (its job, outside its workspace so it can't rewrite it), its own `memory.db`, and a `workspace/` with its `MEMORY.md`. No heartbeat: `ask_agent` files a task in Pip's `agent_tasks` table and starts a runner process, which puts the lane, its notes, its last few tasks (and, for a follow-up, the thread so far) on its page, runs the same loop workers use (pulled out into `runner.py`, so workers now run through it too), appends its end-of-task notes to `MEMORY.md` with the date, writes the report to `workspace/agents/<name>/<id>.md` in Pip's workspace, and the heartbeat wakes Pip with an `agent` event. Its memory (`CrewMemory`) is its own log and workspace with Pip's home for settings, so the vault, search and sources work unchanged while the file tools stay in its folder; `tools.workspace_root` now honors that, and its deletes are logged on Pip's log too, so `DELETE_LIMIT` covers the whole crew. Tools are a fixed `CREW_CORE` plus groups from `AGENT_GROUPS` (sources, vault, email minus sending, calendar, Google files, tasks and contacts, Notion); the test checks every core tool is given or refused on purpose. One task at a time per agent, 3 at once, 20 a day, 10 in a thread. An agent with an `outward` line gets tasks only through the new `agent_task` approval, whose card shows the task word for word (capped at 3,000 chars); `agent_approval` in `home.json` (`outward` default, `always`, `never`, anything else counts as `always`) is the setting that will fold into permission levels. Pip's page lists the roster under "Your agents" when there is one. Live check in a throwaway home: a DeepSeek librarian split a jumbled file by topic in 5 calls and a minute, and wrote itself a note about the convention it chose. Tested in `tests/test_agents.py`. 91 tools.

**Model timeout 5 to 30 minutes** (2026-10-21, `ahab/cli_model.py`, `ahab/watchdog.py`). Codex at max effort on the laptop took longer than the 300-second limit on two wakes running (a repo tour and a startup wake), each lost as "codex took longer than 300 seconds". A CLI model call may now run 30 minutes; the limit only matters for a hung call. The watchdog's stuck-wake threshold went from 90 minutes to 3 hours to match. Workers, agents and the digest use the same limit; web search keeps its own 15 minutes.

**Two model slips forgiven** (2026-10-21, `ahab/tools.py`, `ahab/heartbeat.py`, `tests/test_slips.py`). On the laptop Luna answered the owner's "inspect it" request with a tool call whose `args` was a quoted string, which was refused; its next reply was "waiting for the output" with every field null, which the loop took for a finished wake and slept 30 minutes on, leaving the request unanswered. `tools.run` now reads `args` sent as a quoted JSON object, and a final reply with no tool, no message and no `next_wake_minutes` is asked once more in the same wake (`EMPTY_REPLY`) instead of ending it.

**Status screen: model, tokens, helpers** (2026-10-21, `ahab/console.py`, `ahab/memory.py`, `ahab/days.py`). The second line of the screen now names the model `home.json` picks (`Codex → gpt-6-luna → Max`, read the way Pip's own page reads it) and the tokens spent so far, cut to thousandths of the unit (`14.176 M tokens`, with the in and out split when it fits). Nothing keeps a running total, so the screen adds up what's logged: the closing line of every wake, dream, digest and web search (`memory.TOKEN_STATS` reads all three formats the log has used), plus the `workers` and `agent_tasks` tables. The log is read once and then only its new rows, since it grows for years and the screen redraws every 5 seconds. Running workers and crew-agent tasks get a line each above the services (`helper agent scout  1h30  <what it was asked>`, the task text dropped when the chat is hidden), or "helpers idle · 3 finished in the last day" with any failures in red. Two bugs found on the way: log kinds longer than nine characters (`web_search`, `email_sent`) made a line one column too wide, which wraps on a real screen; and the clock in the corner was wiped by the clear-to-end-of-line that follows a line filling the last column, so the live screen now leaves a two-column margin on the right. `days.py` had the same blind spot as the screen would have had: its token pattern predated the "(N cached)" part and counted none of a wake's tokens, so the day files' totals had read zero; they use the shared pattern now. Tested in `tests/test_console.py` and `tests/test_days.py`.

**Goals designed** (2026-10-21, `docs/DESIGN_GOALS.md`). A goal is an objective Pip works toward across wakes. It combines the keep-going loop from Hermes and OpenClaw with the project folder from Muse, where a goal owns the jobs done for it. There is no judge model, since a second call per wake would roughly double the cost. Instead, each goal has a token budget charged in code, a deadline, check-ins at 50% and 90% of budget, and an evidence line required for "done". Charging works like this: wakes that log progress on a goal are charged to it, a wake that a due goal caused is charged even if Pip ignores the goal, and workers and crew tasks started for a goal charge their tokens to it. A goal's pace wakes Pip the way an alarm does, and `goal_wait` holds it while something outside is pending. Pip opens small goals himself (200k tokens, 14 days, three at once). They show on the status screen, through `/goals` on Telegram and on the day pages, with no ping. Large goals go through a `goal` approval. Pip moves goals forward, and only the owner changes the target: Pip can't edit, pause or drop a goal the owner set or approved. Phase 1 is the record and its machinery. Phase 2 lets goals own their alarms, intents and watches and adds them to the dream's review.
