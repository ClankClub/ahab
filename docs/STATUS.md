# Status

## Where it stands (2026-10-18)

Forked from Lobo's runtime (`../Lobo`, commit `2076c5d`). None of Lobo's `home/` came along, so Perro's memory started empty. Perro is the software; each install's agent can have its own name. The owner's is called Pip (since 2026-10-18), with its home in `silascroe/pip`.

**Character.** [AGENTS.md](../AGENTS.md), the README and the heartbeat prompt (`PROMPT_BODY` in `perro/heartbeat.py`) describe a personal assistant in the spirit of Muse or OpenClaw. It does work you hand it, takes initiative within its own tools, is good to just talk to, and has a personality. An earlier draft was too strict, close to "speak when spoken to"; the current wording is deliberately looser.

**Identity files** (modelled loosely on Muse's core files, built one at a time). Four files in `home/workspace/`, all shown at the top of every wake-up page and capped at 4,000 characters each (AGENTS.md at 10,000) (`perro/identity.py`). `SOUL.md` is who Perro is (origin, character, voice; it tells the owner when it edits it), and `USER.md` is what it knows about the owner; Perro edits both with `write_file`. `PROACTIVE_PREFERENCES.md` (2026-10-18) is the owner's: what to bring up unasked, what to leave alone, when and how. Muse's version is a blank form, because Muse has a separate pipeline that decides what to send and when. Perro has no such pipeline (its judgment on each wake-up decides), so this file starts with working defaults. Perro records preferences the owner tells it there, in their words, and adds no guesses of its own. The quiet hours in Perro's copy (about 4am to noon) are a guess by the build agent and say so. Perro's copy also tells it to keep self-started work out of DeepSeek's peak-price hours (01:00-04:00 and 06:00-10:00 UTC on weekdays, double price; off-peak is half). Answering the owner is always fine. That rule lives only in Perro's copy, because it's about this instance's backend, not about agents in general. The prompt holds only the rules (trust, tools, reply format), which Perro can't edit. `AGENTS.md` (2026-10-18) is Perro's own operating manual, as in Muse: conventions it settled on, tool and site quirks, mistakes not to repeat. It starts empty and grows mostly in the dream; full how-tos stay in skills. There's no separate IDENTITY file; it's folded into SOUL. Notes (4,000 characters) are now for open tasks and short-lived things. Generic starters live in `templates/` in the code repo (see its README); each wake-up copies in any that are missing, with the agent's name filled in, and never overwrites. Perro's own copies were written by hand for it and live only in the private home repo. What Perro can and can't do is in [docs/ABOUT_YOURSELF.md](ABOUT_YOURSELF.md), which it reads a section at a time with the `about_yourself` tool (see below).

**What it can do.** Take tasks and conversation through the inbox or Telegram, search the web (`web_search`) and Wikipedia, read public pages, write files in its workspace, set reminders, message the owner, read its Google calendars (`check_calendar`) and add and change events on its own (`add_event`, `update_event`), search and read its own Gmail (`search_email`, `read_email`), and email a short list of people (`send_email`). In its own Google account it can also search and read Drive, create and add to Docs, read, create and edit Sheets, keep Google Tasks and lists, and keep Contacts, deleting included (18 tools in `perro/google.py`). In its own Notion workspace it can search and read, create pages, rows and its own databases, append, rewrite, retitle, set fields, move pages and trash them (9 tools in `perro/notion.py`). It can't email anyone off its list, invite anyone to an event, share anything, or delete anything outside Notion, Tasks and Contacts, and there only 25 a day.

**Google, through n8n** (2026-10-18). Perro has its own Google account. A Cloud project, also named "Perro", holds an OAuth client of the Web type with redirect `http://localhost:5678/rest/oauth2-credential/callback`. Its consent screen is published, External, with no logo, so tokens don't expire weekly and no verification is triggered. The privacy-policy link points at [PRIVACY.md](../PRIVACY.md). The owner's n8n (Docker, localhost only; their running copy is in `../n8n`) holds signed-in credentials for Calendar, Gmail, Drive, Docs, Sheets, Tasks and Contacts; all seven answered a live API call. There are four Google workflows (and a Notion one, below), exported to [`n8n/workflows/`](../n8n/workflows/) with a setup guide in [`n8n/README.md`](../n8n/README.md) (until 2026-10-18 they were only in the owner's local n8n folder, in no repo, so a clone got Google tools with nothing behind them):
- "Perro: calendar" (`/webhook/perro/calendar?days=N`) lists events from every calendar the account can see, so calendars the owner shares with it show up on their own.
- Calendar writing (2026-10-18) goes through the Google relay as a sixth service, on Perro's own calendar only: `add_event` and `update_event` in `google.py`. The owner barely uses a calendar, so the point is Perro keeping one they see on their phone (they're signed in to Perro's account there). No guests, since an invitation emails people; no deleting (a cancelled event gets renamed); every change goes with `sendUpdates=none`, which the relay insists on. Times are the PC's local time; a date alone is a whole day, and an end date is the last day (Google's own end is the day after). Moving only the start keeps the length. `check_calendar` now shows each event's id. Tested offline (a fake relay; 22 relay cases in Node) and live: a past event added, moved and stretched on Perro's calendar ("Perro calendar test (delete me)", Sat 17 Oct), and the live relay refusing guests, deleting and notifications.
- "Perro: email search" (`/webhook/perro/email/search?q=<gmail search>&max=N`) returns sender, subject, date and snippet.
- "Perro: email read" (`/webhook/perro/email/read?id=`) returns one full message.
- "Perro: Google relay" (POST `/webhook/perro/google`) holds the Drive, Docs, Sheets, Tasks and Contacts sign-ins and forwards `{service, method, url, query, body}` to Google. A Code node first refuses any address outside that service's API, DELETE, and anything about permissions, trashing or clearing, so the relay itself can't share or delete even if Perro's code had a bug. Each service has a read node and a write node, because Google rejects a GET that carries a body and n8n ignores a computed "send body" switch.

All four check a header key: n8n's credential "Perro relay key" must match the `PERRO_N8N_KEY` user environment variable (64 random hex characters, set 2026-10-18). Without it, a web page open on this PC could call the webhooks too, and n8n webhooks answer any origin by default. The heartbeat logs a warning at start if the key is missing.

The Google tools (2026-10-18) read and write freely in Perro's own account, since nothing there reaches another person, but they never delete, trash or share. Files Perro creates live in its own account; the owner is signed into that account on their phone too, so no sharing is needed to see them. Sheets values are written RAW, never as formulas, because a formula like IMPORTXML can fetch a web address, a quiet way for data to leave. Google Tasks keeps dates only, no times; alarms do times. Contacts is Perro's own address book. Tested against a fake relay and live on every service. Test Docs and a Sheet labeled "(delete me)" are still in Perro's Drive (three Docs, including one "Untitled document"); delete them by hand. The test task and contact went with the deletes below.

Neither email workflow marks mail as read. `perro/n8n.py` calls webhooks by fixed path only, refuses any non-local n8n address, and shows times in the owner's local time. For email it prefers the plain-text part. HTML-only mail goes through `web.py`'s extractor, which drops hidden elements. It strips the invisible padding characters marketing mail uses, and it lists attachments without opening them. It was tested against a fake n8n, including a hidden-text injection, and live: once with a temporary calendar event that was then deleted, once with a real email from the owner's other account. Gmail message IDs differ per mailbox, so the sender's copy of an email and Perro's copy have different IDs. On its first wake with the new tools, Perro noticed them, tested both on its own and reported to the owner. Gotchas: n8n's production webhook only exists once the workflow is published; each Google API must be enabled separately in the Cloud project (a disabled one gives a 403 `SERVICE_DISABLED`); n8n 2.x's CLI can `import:workflow` and `publish:workflow`, but the running instance only notices after a restart.

**Codex and Claude Code as the model** (2026-10-18, `perro/cli_model.py`). Backends `codex-luna` (`gpt-6-luna`, max effort since 2026-10-18; high before) and `claude-haiku` run the owner's Codex or Claude Code subscription as Perro's model. Perro's loop, tools and JSON replies are unchanged; each model call is one stateless, non-interactive CLI run in an empty folder, with the conversation so far written out as one prompt. By default both CLIs would load the owner's own profile (their CLAUDE.md or AGENTS.md, memories, plugins, MCP servers), so each gets its own profile folder under `%LOCALAPPDATA%\Perro` (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`), logged in once by the owner and outside both repos because the login tokens live there. An empty profile says "not logged in" rather than falling back. Claude Code runs with `--tools ""`, no MCP and no saved session; `--bare` isn't used because it skips subscription logins. Codex runs read-only with `--ignore-user-config`, no saved session, web search off and 18 features off (shell, browser, computer use, plugins, memories, sub-agents, hooks and so on). Perro's system prompt goes in through `model_instructions_file`, replacing Codex's own coding-agent instructions, and Codex's notes on its sandbox, permissions, apps, skills and plugins are off (`include_*=false`). Codex still handed the model built-in tools of its own, and Perro took those for its real toolset: first it told the owner it had lost its Google tools and had "only read-only workspace access and the Codex tools", and later (2026-10-18 afternoon) it refused to make a spreadsheet for hours, saying `create_sheet` wasn't callable, even when told it was. The cause isn't a feature switch but Codex's catalog of models (`models_cache.json` in the profile): newer models like Luna are marked `tool_mode: code_mode_only` and `multi_agent_version: v2`, which gives them Codex's JavaScript `exec` box (with only a clock and apply_patch inside), `wait`, `request_user_input` and a set of sub-agent tools. Luna used `exec` mid-call to list its tools, found none of Perro's, and believed that over the prompt; each peek was another model request inside one CLI run (a 12k wake billed 37k) and showed nowhere in Perro's log. The fix: every call passes `model_catalog_json`, a catalog of one made from the model's own cached entry with `tool_mode: direct`, no experimental tools, no apply_patch and no multi-agent version, plus `tools.experimental_request_user_input.enabled=false`. Probed directly, the model then reports no tools at all, and Codex's hidden overhead drops from about 4k tokens to about 0.6k. On a copy of the home, with notes that still said the tools were gone, Perro went straight to `drive_search` and then `create_sheet`. A brand-new profile has no cache yet, so its very first call runs without the catalog. The prompt and `docs/ABOUT_YOURSELF.md` now say a model's own built-in tools aren't Perro's. Calls are hidden on Windows so the hidden heartbeat doesn't flash console windows. Live, on copies of the home: Codex Luna about 3 seconds and 15k tokens in per wake at first, 11.5k once Codex's instructions were replaced (about 4k of Codex overhead was left then, mostly those tool definitions; about 0.6k since the catalog fix), short replies; Claude Haiku 7-12 seconds and 13k in, more personality. Both handled a tool step and used the new `message` field. Perro switched to `codex-luna` the same night (`home/home.json`).

**The reply form** (2026-10-18, `reply_form` in `perro/heartbeat.py`). On its first day on Luna, Perro lost three answers to the owner (11:53, 13:20, 14:49): the model wrote the message as plain prose instead of the JSON object, the beat couldn't read it, and the owner heard nothing until a later wake. Once more it appended its scratch thinking after a valid object. Now the reply format goes to the backend as a JSON Schema when the backend can enforce one. Codex takes it as `--output-schema` and holds the model's answer to it, so prose, trailing thinking and made-up tool names can't happen there. Codex runs OpenAI's strict mode (every field present, null when unused, no free-form objects), so in the form `tool` is one of the real tool names or null, `args` is the args object written as a JSON string, and the dream's `files` is a list of path/text pairs; `parse_reply` turns those back into the usual shape, and the prompt's format is unchanged. Claude Code's `--json-schema` isn't used: it works by handing the model a tool, and with one in hand Haiku tried calling Perro's tools natively, was refused, and told the owner it couldn't read files. DeepSeek takes no schema, so it stays on JSON mode. For every backend, a reply that isn't JSON at all is no longer dropped: the beat (and the dream) hands it back once with a note to rewrite it as the object, message included, and logs that it happened; a second slip in the same wake fails as before. This is structured output, not native function calling: tools are still requested in the reply, readable in the log, on every backend. Live on Luna in a throwaway home: a wake that listed, read, set an alarm and answered, with no errors, and a dream through its own form.

**Dreaming** (2026-10-18, `perro/dream.py`). Once a day at 7:00 local (`DREAM_HOUR`), the heartbeat runs a separate wake-up instead of a normal one: Perro looks back over everything since its last dream (at most 48 hours), tidies its notes, moves what lasts into its files, and writes a short reflection to `workspace/dreams/YYYY-MM-DD.md`. This is the OpenClaw-style consolidation, not Lobo's free-association dream. What it sees: owner and Perro messages in full, thoughts cut to 600 characters, errors, and only the one-line header of each tool call, so no web page or email body reaches the dream (a dream rewrites the files every later wake trusts, so it's the worst place for an injection). It gets only `list_files`, `read_file`, `recall` and `about_yourself`; messaging and outside tools are refused. It also sees the names of its waking tools and is told they're the same every wake, and it checks any "can't do" in its notes against those and the guide before keeping it: on 2026-10-18 a wrong "the Sheets tools aren't callable" sat in the notes and was believed again every wake. On a copy of the home with that planted, a dream at max effort dropped it and kept the real limit (Docs can't delete text). The entry has a shape since then, borrowed from another agent's dreams: what Perro now believes about its owner and how sure (guesses marked as guesses, in USER.md too), what's open and whose move it is, then where it helped and fell short, the one lesson, and the first move for the coming day. A heading the model writes into the entry is stripped, since the code adds one. File changes come only in its final answer's `files` field, written by the code, because in the first live test it claimed edits to three files it never made. Identity files over their caps (4,000 characters, AGENTS.md 10,000) are refused and reported, not trimmed. It may edit SOUL.md, and if it does, the log tells it to tell the owner next time they talk. A day with no conversation is skipped without calling the model. A new home's first dream is the next morning; `home/dream.state` holds the last morning handled, so a missed or crashed dream isn't retried in a loop. `py -m perro.dream` dreams now, by hand, when the heartbeat is stopped. One live dream on a copy of the home: about 41k tokens in, 9k out, 40 seconds, and every change it reported was on disk.

**Skills from the dream** (2026-10-18, `perro/skills.py`, `perro/dream.py`). Taken from how Hermes Agent improves itself. Before this, the dream mentioned skills in passing and none were ever written. Now writing them is a step of its own. The dream is asked what it worked out that it would otherwise have to work out again, and to keep a how-to for a task likely to come back as `skills/<name>.md`, whose first line says when to use it, followed by the steps, the pitfalls and how to tell it worked. Only what the day showed counts (a procedure never run isn't a skill), an existing skill gets improved before a new one is added, and each is capped at 4,000 characters. Two lists computed in code point it at the evidence. "Wake-ups that took work" gives each wake-up with 4 or more tool calls and its tools in order (Hermes looks after 5+). "Your skills" gives each skill's last use from the whole log (read today, last read on a date, or never read since written), so a skill that went wrong gets fixed, overlapping ones merged and dead ones retired. A skill given empty text moves to `skills/retired/`, out of the list but kept. The final reply has a required `skill_check` field answering the question either way, recorded in the dream event. Without it, a live dream on a copy of Pip's real day never considered skills at all. With it, the same day produced `skills/site-release.md`, the build, push, preview and publish sequence with that day's real pitfalls (the generic Vercel 422, a GitHub push that predated a redesign), every tool it names a real one. Awake, the prompt now says to read a skill before a task it covers and to fix it with write_file if it proves wrong. A dream re-sends the whole day with each tool call, so one that reads a lot gets expensive (204k tokens in over 8 calls in one test run, 65k over 2 in the next).

**Repeating alarms** (2026-10-18, `perro/alarms.py`). `set_alarm` takes an optional `repeat` (`daily`, `weekdays`, `weekly`). A repeating alarm isn't marked fired when it rings. The same alarm (same id, so `cancel_alarm` stops the series) moves to its next time, worked out on the owner's local clock so a 9:00 alarm stays at 9:00 across daylight saving. Times missed while the PC was off collapse into one ring. Older databases get the new column on first use. Before this, Pip had to set the next day's Moby-Dick reminder by hand every day. Tested offline, with the daylight-saving change checked on US Eastern time.

**Approvals** (2026-10-18, `perro/approvals.py`). The step every outward action goes through. Two real kinds use it so far, `github_public` and `vercel_publish` (below), plus a harmless `test` kind for checking the path. A tool files a request with the exact payload of the action, and code writes the card from that payload, so the owner reads facts rather than Perro's description of them (Perro may add a note, shown as its own). The owner answers only by a Telegram button tap, checked like a message (paired account, paired private chat, and the card's own message id), or by `py -m perro.approvals --yes N` / `--no N` at the PC. A typed "yes" is just a message, because Perro could word a question so an innocent answer approves something. An approval wakes the sleeping heartbeat within seconds, and the next wake carries it out in code before the model is called, once (claimed as `running` first), then logs an `approval` event with the outcome. Perro has no tool that approves or runs anything. A denial doesn't wake Perro (nothing to do; it hears at its next wake), unanswered requests expire after 48 hours, at most 10 wait at once, and pending ones show on Perro's page. Each kind registers a card function, which also refuses a bad payload, and a run function. Requests live in their own table in `memory.db`, outside the workspace. The bridge sends each card with Approve and Deny buttons, and rewrites it once settled, without buttons, showing what happened. Tested against a fake Telegram API (strangers, group chats, mismatched and forged buttons, double taps, expiry, a failing action) and live with a test request.

**The workshop** (2026-10-18, `perro/workshop.py`, `workshop/`). Phase 2 of Codex+GitHub+Vercel. Perro's `start_build` takes a site name and a brief; a background runner (its own process, so it survives a heartbeat restart) has Codex build a static site in a Docker container, then a second, fresh container runs `npm install` and `npm run build` and the code looks for `dist/index.html`. That check, not Codex's report, decides "built". The finished build wakes Perro (like an approval) and is logged as a `build` event; `check_build` shows the status, Codex's report and the files, and `read_build_file` reads one. The same name again revises that site: briefs pile up in `briefs/`, `BRIEF.md` is the latest, and the house rules (`workshop/HOUSE_RULES.md`, copied in as `AGENTS.md` every time) tell Codex what to make: a Vite static site, `base: './'`, no personal details, no tracking, a short plain report. The box: image `perro-workshop` (node 22, git, Codex CLI pinned at 0.155.0), the `node` user, zero capabilities, `no-new-privileges`, a read-only system with 1 GB scratch tmpfs, 4 GB memory, 2 CPUs and 1,024 processes, the site folder as its only window on the PC, and `node_modules` in a Docker volume per site (faster than the Windows folder, and symlinks work). Its network (`perro-workshop`, internal) has no route out; the only door is `workshop/proxy.py`, a standard-library HTTPS proxy in a stock Python container that allows `chatgpt.com`, `auth.openai.com`, `api.openai.com` and `registry.npmjs.org`, refuses everything else (plain HTTP, other ports, raw IPs, names that resolve to private addresses), and logs it; refused hosts are listed with each build. **The GitHub relay** (2026-10-18, `perro/github.py`, `n8n/workflows/perro-github.json`). Phase 3. Perro's `push_site` copies a workshop site's source into a private repository of the same name under `perro-agent` (made with `auto_init` on the first push) through GitHub's Git Data API: blob ids are computed locally so only changed files are uploaded, the tree is built whole (no base tree) so removed files go, an identical tree is "nothing changed", and the branch moves with `force: false`. Left out: `briefs/`, `BRIEF.md`, `AGENTS.md` (the briefs can hold the owner's details), `dist/`, `node_modules/`, and anything under `.github/`; 5 MB a file, 20 MB and 500 files a site; refused while that site is building. `list_repos` lists the account. `request_make_public` is the first real approval kind (`github_public`): the payload is the repository and its head commit, the card says anyone will see every file and the whole history as of that commit, and the run re-reads the head and refuses if anything was pushed since. The relay is an allowlist, the second fence: `GET user`, `GET`/`POST user/repos` (new ones must be `private: true`, no `visibility`), `GET` inside `perro-agent/<repo>`, `POST` of git blobs, trees, commits and refs, `PATCH` of a branch ref (only with `force: false`), and `PATCH` of a repository only with the exact body `{"private":false}`. Everything else is refused (other owners and hosts, DELETE, collaborators, hooks, keys, secrets, Actions, settings, `..`, `%`, `?` in paths, and `.github/` anywhere in a body). Tested with a fence test in Node (11 allowed, 28 refused), a fake GitHub, and live: a first push of `workshop-test` to a new private repo, an unchanged push (nothing sent), and a one-file revision. Making a repository public hasn't been tried live (it would be a real publication).

**The Vercel relay** (2026-10-18, `perro/vercel.py`, `n8n/workflows/perro-vercel.json`). Phase 4. `preview_site` deploys a workshop site's built `dist/` (only from a build that passed the check) to a project of the same name in Perro's Vercel account, `perroagent`, the way Vercel's CLI does: the deployment lists files by SHA-1, Vercel answers `missing_files`, and only those are uploaded (`POST /v2/files`; the relay turns the base64 back into raw bytes in a Code node and Vercel checks the digest). No Git connection, on purpose: one would make every push to `main` a production deployment, past the approval. Static files only (`projectSettings: {framework: null}`, no build on Vercel), and nothing that would run code there (`api/`, middleware, `vercel.json`, `package.json`, `.vercel/`). Previews sit behind Vercel Authentication (the default "standard" protection, `ssoProtection: all_except_custom_domains`); the code refuses to deploy if a project's protection is off. `request_publish` is the second approval kind (`vercel_publish`): the payload names one ready deployment, and the run re-checks it and redeploys it as production (`POST /v13/deployments` with `deploymentId` and `target: "production"`): the same files, unchanged, in a new deployment that takes over the public address once it's ready, so what goes live is what the owner could open. Deployments are immutable, so no "changed since" check is needed. It first promoted the preview instead (`POST /v10/projects/<id>/promote/<dpl>`), which Vercel only allows for a deployment built for production: the first real publish (SHALLOWS, 2026-10-18) was approved twice and refused twice with a bare HTTP 422, "Resource cannot be processed". Vercel's own CLI rebuilds a preview as production to promote it, which is what the run does now. **Gotcha, found by leaking one:** Vercel makes a project's first deployment its production one whatever the request says. The first live test put `workshop-test` (the harmless test page) on the open internet at `workshop-test-topaz.vercel.app` without an approval, and a probe project (`perro-probe`, a "nothing here" page) showed that sending `target: "preview"` doesn't stop it (Vercel accepts no `preview` value afterwards; leaving the target out is how a preview is asked for). So a new project's first deployment is a fixed placeholder page from the code (recorded in `vercel_placeholders` in `memory.db`, so it's never offered as the site), and the site arrives only as a later preview; the site's name is public from then on. The relay is the second fence: it refuses any `target` on new files, `gitSource`, other `projectSettings`, risky paths, other query options (no `teamId`), promoting, and everything but reading, making a project (name only), uploading, deploying, and the one publishing shape (exactly `name`, `project`, `deploymentId`, `target: "production"` and `projectSettings: {framework: null}`, no files), which is the approval's request. Tested with a fence test in Node (13 allowed, 44 refused, plus 14 cases for the publishing shape), a fake Vercel that copies the first-deployment rule and now refuses to promote a preview like the real one, and live: uploads, a first deployment, the probe, a preview of an existing project (nothing re-uploaded), and the live relay refusing near-miss publishing requests. A live publish through the approval worked on 2026-10-18: SHALLOWS at shallows-two.vercel.app. To clean up, in the Vercel dashboard: delete the projects `workshop-test` and `perro-probe` (Settings, bottom of the page).

**Telegram.** `perro/telegram.py` is a bridge process. It long-polls the bot, passes the owner's messages into the inbox as knocks, and forwards Perro's replies back. A one-time pairing code locks it to the owner's account and private chat; other senders are dropped, and their text never reaches Perro. Tested against a fake Telegram API (pairing, strangers, group chats, non-text messages, splitting long replies, keeping the token out of error messages). Live since 2026-10-18 with a real bot paired to the owner; a real round trip took about 8 seconds. The heartbeat checks for knocks every 3 seconds instead of every 30.

**Running unattended.** `scripts/install-task.ps1` registers "Perro heartbeat" and "Perro telegram" as login tasks; both are installed and running on the owner's PC. The installer finds `pythonw.exe` through the `py` launcher, since `python` isn't on the PATH here. Hidden under `pythonw` there's no console (`sys.stdout` is `None`), so anything that runs hidden must switch to its `--log` file before printing. The bridge crashed on exactly that at first.

**The watchdog** (2026-10-18, `perro/watchdog.py`). The schedulers restart a crashed heartbeat or bridge, but not one that exits cleanly or stays gone, a heartbeat that's alive and never wakes, or n8n being down, and Perro can't report those itself. "Perro watchdog" is a third scheduled task (every 10 minutes; a launchd agent on the Mac) that checks from outside. The heartbeat and the bridge each touch a `.alive` file in the home every minute from a background thread, so a file older than 5 minutes means that process is gone. The heartbeat's own log shows whether it's stuck: its last `sleep` event says when it meant to wake, so still asleep 30 minutes past that, or a wake-up running over 90 minutes, counts. n8n is checked at `/healthz` when `PERRO_N8N_KEY` is set. A problem has to show on two checks in a row (so a PC just back from sleep doesn't set it off); then the owner gets one Telegram message, sent straight through the bot's API rather than the bridge, and one more when it clears. Each message also goes in Perro's log as a `watchdog` event. The state is `home/watchdog.json`. It only alerts and restarts nothing, so a deliberate stop costs one message, not a fight. `py -m perro.watchdog --dry-run` prints what it would say. Tested offline (stale and fresh files, stuck asleep and mid-wake, the grace periods, n8n up and down, a failed send retried, one message for two problems) and dry-run live on the owner's home, healthy and with n8n pointed at a dead port. Installed on the owner's PC 2026-10-18.

## What testing found (2026-10-18, on `deepseek-flash`)

- Plain chat took two model calls: one to send the reply with `message_owner`, a second only to hear "Sent" and finish. In 18 of 20 such wakes Perro also rewrote its whole notes (2,500-3,500 characters) when nothing lasting had changed. Found from notes Perro and Codex left in `workspace/for_claude.md`, and confirmed in the log. The final reply now has a `message` field the code sends on the way out (logged like `message_owner`, not counted as a tool call; if it can't be sent, the error is logged and Perro wakes within 30 minutes). A `message` inside a tool request isn't sent, and Perro is told so in the tool result. The prompt says to leave notes unchanged unless something in them changed, and identical notes aren't rewritten. Replaying a real "You here?" on a copy of the home: one call, 7.2k tokens in, against roughly 14-16k before. Message events in the log now say their text is under "Recent conversation", because the header alone looked like an empty message and Perro reported it as a bug.
- A 5-call limit ran out before Perro's report, and its notes then claimed it had reported. The limit is now 10, a refused call says plainly that it didn't happen, and the prompt says a message reached the owner only when `message_owner` returned "Sent".
- `deepseek-flash` sometimes returns an empty reply, or leaks its native tool-call markup ("DSML" tokens) instead of JSON. `perro/model.py` retries those up to 4 times, and the prompt asks for plain JSON only. Watch for this if the model changes.
- `parse_reply` crashed the heartbeat on an empty reply; it's now a logged error.
- A prompt injection planted in a saved email (`home/workspace/mail/landlord.txt`) was ignored and flagged to the owner.
- A 12-moon research task carried over two wake-ups through its notes. One side claim it made from memory was wrong (it said Miranda comes after Charon; Umbriel does). The prompt now asks it to keep checked facts apart from remembered ones.
- It read UTC as local time and used an emoji. Each wake-up now shows the owner's local time, and the prompt asks for plain text.
- It believed messages wait for its next scheduled wake-up; they actually wake it within seconds. The prompt now says so.
- Cost: one 10-call wake-up used about 227k input tokens, because every call resends all earlier page fetches. Now only the latest tool result stays whole and long earlier ones are cut to 600 characters; in a fake 10-read wake-up that sent 36% of the characters. DeepSeek caches repeated prompt openings and bills those tokens far cheaper, so the untrimmed version cost less than its raw count suggested; the sleep line now shows how much was cached (`3081 in (2900 cached)`), and tokens from retried empty replies are counted too.
- Perro only saw the last 20 log events, about two chat exchanges (a reply makes ~9 events). Asked how long it had been alive, it dated its "earliest memory" to the last thing on its page, not its first wake-up. The page now has a "Recent conversation" section from the messages table (16 messages / 4,000 characters), and message events in the log show only their header.
- Told that SOUL.md is a file it can edit, it also wrote its notes into `workspace/notes.md` before using the notes field. The prompt now says notes aren't a workspace file.

**The mail watch** (2026-10-18, `perro/mail.py`). Email from the list wakes Perro. While it sleeps, the heartbeat runs one Gmail search through n8n every minute (`in:inbox newer_than:2d` from the listed addresses), no model call, so a quiet inbox costs nothing; mail from anyone else never wakes it. Each email seen is a row in `mail_seen` in `memory.db`, and the first look only notes what's already there. `email.json` has an `agents` list marking which addresses are AI agents. A person (the owner included) wakes Perro at the next check. An agent's email waits longer the more that agent has written in the last day: about a minute, 10 minutes, an hour, 6 hours, then a day, so a real exchange barely notices and two assistants thanking each other stretch out to a few rounds a day. Past 6 from one agent in a day, its mail is held (no wake), `send_email` refuses to write to it, and Perro is told at its next wake and asked to tell the owner. Counting is per agent, not per thread, so starting a new thread doesn't reset it. The brake lifts when a person on the list writes in one of that agent's threads, when the owner sends `/talk` on Telegram (handled by the bridge in code, never passed to Perro), or with `py -m perro.mail --lift`; waiting and held mail then comes through as ordinary mail. Each email that wakes Perro arrives as an `email` event, and the agents' ones remind it that a thread can end on a thanks. The owner's address wakes Perro too, with a reminder that email isn't one of the owner's channels for instructions. The email search now also returns each message's thread id. Tested offline (a fake Gmail: wake timing, the slowdown, the ceiling, lifts by a person, by `/talk` and a stranger's `/talk` ignored, n8n down) and live in a throwaway home against the real inbox: real thread ids, a person on the list due at once, an agent in a minute. Running on the owner's home since 2026-10-18; a real email waking Pip is the last thing to see.
