# Status

## Where it stands (2026-10-18)

Forked from Lobo's runtime (`../Lobo`, commit `2076c5d`). None of Lobo's `home/` came along, so Perro's memory started empty.

**Character.** [AGENTS.md](../AGENTS.md), the README and the heartbeat prompt (`PROMPT_BODY` in `perro/heartbeat.py`) describe a personal assistant in the spirit of Muse or OpenClaw. It does work you hand it, takes initiative within its own tools, is good to just talk to, and has a personality. An earlier draft was too strict, close to "speak when spoken to"; the current wording is deliberately looser.

**Identity files** (modelled loosely on Muse's core files, built one at a time). Four files in `home/workspace/`, all shown at the top of every wake-up page and capped at 4,000 characters each (AGENTS.md at 10,000) (`perro/identity.py`). `SOUL.md` is who Perro is (origin, character, voice; it tells the owner when it edits it), and `USER.md` is what it knows about the owner; Perro edits both with `write_file`. `PROACTIVE_PREFERENCES.md` (2026-10-18) is the owner's: what to bring up unasked, what to leave alone, when and how. Muse's version is a blank form, because Muse has a separate pipeline that decides what to send and when. Perro has no such pipeline (its judgment on each wake-up decides), so this file starts with working defaults. Perro records preferences the owner tells it there, in their words, and adds no guesses of its own. The quiet hours in Perro's copy (about 4am to noon) are a guess by the build agent and say so. Perro's copy also tells it to keep self-started work out of DeepSeek's peak-price hours (01:00-04:00 and 06:00-10:00 UTC on weekdays, double price; off-peak is half). Answering the owner is always fine. That rule lives only in Perro's copy, because it's about this instance's backend, not about agents in general. The prompt holds only the rules (trust, tools, reply format), which Perro can't edit. `AGENTS.md` (2026-10-18) is Perro's own operating manual, as in Muse: conventions it settled on, tool and site quirks, mistakes not to repeat. It starts empty and grows mostly in the dream; full how-tos stay in skills. There's no separate IDENTITY file; it's folded into SOUL. Notes (4,000 characters) are now for open tasks and short-lived things. Generic starters live in `templates/` in the code repo (see its README); each wake-up copies in any that are missing, with the agent's name filled in, and never overwrites. Perro's own copies were written by hand for it and live only in the private home repo. What Perro can and can't do is in [docs/ABOUT_YOURSELF.md](ABOUT_YOURSELF.md), which it reads a section at a time with the `about_yourself` tool (see below).

**What it can do.** Take tasks and conversation through the inbox or Telegram, research on the public web and Wikipedia, write files in its workspace, set reminders, message the owner, read its Google calendars (`check_calendar`), and search and read its own Gmail (`search_email`, `read_email`). In its own Google account it can also search and read Drive, create and add to Docs, read, create and edit Sheets, keep Google Tasks, and search and add Contacts (13 tools in `perro/google.py`). In its own Notion workspace it can search, read pages, rows and databases, create pages and rows, append to them and change titles and fields (5 tools in `perro/notion.py`). It can't send email, delete anything or share anything yet.

**Google, through n8n** (2026-10-18). Perro has its own Google account. A Cloud project, also named "Perro", holds an OAuth client of the Web type with redirect `http://localhost:5678/rest/oauth2-credential/callback`. Its consent screen is published, External, with no logo, so tokens don't expire weekly and no verification is triggered. The privacy-policy link points at [PRIVACY.md](../PRIVACY.md). The owner's n8n (Docker, localhost only; their running copy is in `../n8n`) holds signed-in credentials for Calendar, Gmail, Drive, Docs, Sheets, Tasks and Contacts; all seven answered a live API call. There are four Google workflows (and a Notion one, below), exported to [`n8n/workflows/`](../n8n/workflows/) with a setup guide in [`n8n/README.md`](../n8n/README.md) (until 2026-10-18 they were only in the owner's local n8n folder, in no repo, so a clone got Google tools with nothing behind them):
- "Perro: calendar" (`/webhook/perro/calendar?days=N`) lists events from every calendar the account can see, so calendars the owner shares with it show up on their own.
- "Perro: email search" (`/webhook/perro/email/search?q=<gmail search>&max=N`) returns sender, subject, date and snippet.
- "Perro: email read" (`/webhook/perro/email/read?id=`) returns one full message.
- "Perro: Google relay" (POST `/webhook/perro/google`) holds the Drive, Docs, Sheets, Tasks and Contacts sign-ins and forwards `{service, method, url, query, body}` to Google. A Code node first refuses any address outside that service's API, DELETE, and anything about permissions, trashing or clearing, so the relay itself can't share or delete even if Perro's code had a bug. Each service has a read node and a write node, because Google rejects a GET that carries a body and n8n ignores a computed "send body" switch.

All four check a header key: n8n's credential "Perro relay key" must match the `PERRO_N8N_KEY` user environment variable (64 random hex characters, set 2026-10-18). Without it, a web page open on this PC could call the webhooks too, and n8n webhooks answer any origin by default. The heartbeat logs a warning at start if the key is missing.

The Google tools (2026-10-18) read and write freely in Perro's own account, since nothing there reaches another person, but they never delete, trash or share. Files Perro creates live in its own account; the owner is signed into that account on their phone too, so no sharing is needed to see them. Sheets values are written RAW, never as formulas, because a formula like IMPORTXML can fetch a web address, a quiet way for data to leave. Google Tasks keeps dates only, no times; alarms do times. Contacts is Perro's own address book. Tested against a fake relay and live on every service. Test items labeled "(delete me)" are still in Perro's account (three Docs, including one "Untitled document", one Sheet, one task, one contact), because Perro's tools can't delete and the build agent's direct cleanup was blocked; delete them by hand.

Neither email workflow marks mail as read. `perro/n8n.py` calls webhooks by fixed path only, refuses any non-local n8n address, and shows times in the owner's local time. For email it prefers the plain-text part. HTML-only mail goes through `web.py`'s extractor, which drops hidden elements. It strips the invisible padding characters marketing mail uses, and it lists attachments without opening them. It was tested against a fake n8n, including a hidden-text injection, and live: once with a temporary calendar event that was then deleted, once with a real email from the owner's other account. Gmail message IDs differ per mailbox, so the sender's copy of an email and Perro's copy have different IDs. On its first wake with the new tools, Perro noticed them, tested both on its own and reported to the owner. Gotchas: n8n's production webhook only exists once the workflow is published; each Google API must be enabled separately in the Cloud project (a disabled one gives a 403 `SERVICE_DISABLED`); n8n 2.x's CLI can `import:workflow` and `publish:workflow`, but the running instance only notices after a restart.

**Codex and Claude Code as the model** (2026-10-18, `perro/cli_model.py`). Backends `codex-luna` (`gpt-6-luna`, high effort) and `claude-haiku` run the owner's Codex or Claude Code subscription as Perro's model. Perro's loop, tools and JSON replies are unchanged; each model call is one stateless, non-interactive CLI run in an empty folder, with the conversation so far written out as one prompt. By default both CLIs would load the owner's own profile (their CLAUDE.md or AGENTS.md, memories, plugins, MCP servers), so each gets its own profile folder under `%LOCALAPPDATA%\Perro` (`CODEX_HOME`, `CLAUDE_CONFIG_DIR`), logged in once by the owner and outside both repos because the login tokens live there. An empty profile says "not logged in" rather than falling back. Claude Code runs with `--tools ""`, no MCP and no saved session; `--bare` isn't used because it skips subscription logins. Codex runs read-only with `--ignore-user-config`, no saved session, web search off and 18 features off (shell, browser, computer use, plugins, memories, sub-agents, hooks and so on). Perro's system prompt goes in through `model_instructions_file`, replacing Codex's own coding-agent instructions, and Codex's notes on its sandbox, permissions, apps, skills and plugins are off (`include_*=false`). Before that, Perro on Codex told the owner it had lost its Google tools and had "only read-only workspace access and the Codex tools": Codex still hands the model hollow tool definitions of its own (`exec` with no command tool inside, `wait`, `request_user_input`, sub-agent tools) that no setting found removes, and the model took those for its real toolset. Probed directly, no shell runs and no sub-agent starts, but `exec` is live: it's Codex's JavaScript "code mode", and Luna often uses it mid-call to list its own tools (`ALL_TOOLS`), which shows only in Codex's session record, never in Perro's log. Each such peek is a second model request inside one CLI run, so that call bills about 23k in instead of 11.5k; it happened on most first calls of a wake in testing, ordinary questions included. `--disable code_mode_host` only makes the call fail (same cost), and no switch found removes the tool. Left as is, since Luna runs on the owner's subscription. The prompt and `docs/ABOUT_YOURSELF.md` now say a model's own built-in tools aren't Perro's. Calls are hidden on Windows so the hidden heartbeat doesn't flash console windows. Live, on copies of the home: Codex Luna about 3 seconds and 15k tokens in per wake at first, 11.5k once Codex's instructions were replaced (about 4k of Codex overhead is left, mostly those tool definitions), short replies; Claude Haiku 7-12 seconds and 13k in, more personality. Both handled a tool step and used the new `message` field. Perro switched to `codex-luna` the same night (`home/home.json`).

It has its own workflow rather than a sixth service in the Google relay because its fence is different: Notion deletes by PATCHing `archived` or `in_trash`, not with DELETE. Its Code node passes only the `search`, `pages`, `blocks` and `databases` paths, only GET, POST and PATCH, and refuses any body that mentions archiving or trashing; tested live against each. Perro's workspace is Notion's starter template (Docs, Projects, Meetings, Notes, Tasks and People databases), so every page is a database row, and the tools treat rows as the normal case: reading a database shows its fields (with status and select options) and its 50 most recently edited rows, and creating a page in a database takes fields by name, converted by the database's own types. Relations, people, files and formulas can't be set. Page text goes both ways as lines with markdown-ish prefixes (`# `, `- `, `1. `, `[ ] `, `> `, ```), one block per line, so what Perro reads it can write back; reading follows nested blocks two levels deep, up to 300 blocks. Ids come as ids or as pasted Notion links. Tested against a fake relay and live: search, two databases, two rows, a create with body text, an append, a rename, a status and a date set, changed and cleared, and both kinds of refusal. **Dreaming** (2026-10-18, `perro/dream.py`). Once a day at 7:00 local (`DREAM_HOUR`), the heartbeat runs a separate wake-up instead of a normal one: Perro looks back over everything since its last dream (at most 48 hours), tidies its notes, moves what lasts into its files, and writes a short reflection to `workspace/dreams/YYYY-MM-DD.md`. This is the OpenClaw-style consolidation, not Lobo's free-association dream. What it sees: owner and Perro messages in full, thoughts cut to 600 characters, errors, and only the one-line header of each tool call, so no web page or email body reaches the dream (a dream rewrites the files every later wake trusts, so it's the worst place for an injection). It gets only `list_files`, `read_file` and `recall`; messaging and outside tools are refused. File changes come only in its final answer's `files` field, written by the code, because in the first live test it claimed edits to three files it never made. Identity files over their caps (4,000 characters, AGENTS.md 10,000) are refused and reported, not trimmed. It may edit SOUL.md, and if it does, the log tells it to tell the owner next time they talk. A day with no conversation is skipped without calling the model. A new home's first dream is the next morning; `home/dream.state` holds the last morning handled, so a missed or crashed dream isn't retried in a loop. `py -m perro.dream` dreams now, by hand, when the heartbeat is stopped. One live dream on a copy of the home: about 41k tokens in, 9k out, 40 seconds, and every change it reported was on disk.

**Approvals** (2026-10-18, `perro/approvals.py`). The step every outward action will go through; nothing real uses it yet, so it has a harmless `test` kind. A tool files a request with the exact payload of the action, and code writes the card from that payload, so the owner reads facts rather than Perro's description of them (Perro may add a note, shown as its own). The owner answers only by a Telegram button tap, checked like a message (paired account, paired private chat, and the card's own message id), or by `py -m perro.approvals --yes N` / `--no N` at the PC. A typed "yes" is just a message, because Perro could word a question so an innocent answer approves something. An approval wakes the sleeping heartbeat within seconds, and the next wake carries it out in code before the model is called, once (claimed as `running` first), then logs an `approval` event with the outcome. Perro has no tool that approves or runs anything. A denial doesn't wake Perro (nothing to do; it hears at its next wake), unanswered requests expire after 48 hours, at most 10 wait at once, and pending ones show on Perro's page. Each kind registers a card function, which also refuses a bad payload, and a run function. Requests live in their own table in `memory.db`, outside the workspace. The bridge sends each card with Approve and Deny buttons, and rewrites it once settled, without buttons, showing what happened. Tested against a fake Telegram API (strangers, group chats, mismatched and forged buttons, double taps, expiry, a failing action) and live with a test request.

**Telegram.** `perro/telegram.py` is a bridge process. It long-polls the bot, passes the owner's messages into the inbox as knocks, and forwards Perro's replies back. A one-time pairing code locks it to the owner's account and private chat; other senders are dropped, and their text never reaches Perro. Tested against a fake Telegram API (pairing, strangers, group chats, non-text messages, splitting long replies, keeping the token out of error messages). Live since 2026-10-18 with a real bot paired to the owner; a real round trip took about 8 seconds. The heartbeat checks for knocks every 3 seconds instead of every 30.

**Running unattended.** `scripts/install-task.ps1` registers "Perro heartbeat" and "Perro telegram" as login tasks; both are installed and running on the owner's PC. The installer finds `pythonw.exe` through the `py` launcher, since `python` isn't on the PATH here. Hidden under `pythonw` there's no console (`sys.stdout` is `None`), so anything that runs hidden must switch to its `--log` file before printing. The bridge crashed on exactly that at first.

## What testing found (2026-10-18, on `deepseek-flash`)

- Plain chat took two model calls: one to send the reply with `message_owner`, a second only to hear "Sent" and finish. In 18 of 20 such wakes Perro also rewrote its whole notes (2,500-3,500 characters) when nothing lasting had changed. Found from notes Perro and Codex left in `workspace/for_claude.md`, and confirmed in the log. The final reply now has a `message` field the code sends on the way out (logged like `message_owner`, not counted as a tool call; if it can't be sent, the error is logged and Perro wakes within 30 minutes). A `message` inside a tool request isn't sent, and Perro is told so in the tool result. The prompt says to leave notes unchanged unless something in them changed, and identical notes aren't rewritten. Replaying a real "You here?" on a copy of the home: one call, 7.2k tokens in, against roughly 14-16k before. Message events in the log now say their text is under "Recent conversation", because the header alone looked like an empty message and Perro reported it as a bug.
- A 5-call limit ran out before Perro's report, and its notes then claimed it had reported. The limit is now 10, a refused call says plainly that it didn't happen, and the prompt says a message reached the owner only when `message_owner` returned "Sent".
- `deepseek-flash` sometimes returns an empty reply, or leaks its native tool-call markup ("DSML" tokens) instead of JSON. `perro/model.py` retries those up to 4 times, and the prompt asks for plain JSON only. Watch for this if the model changes.
- `parse_reply` crashed the heartbeat on an empty reply; it's now a logged error.
- A prompt injection planted in a saved email (`home/workspace/mail/landlord.txt`) was ignored and flagged to the owner.
- A 12-moon research task carried over two wake-ups through its notes. One side claim it made from memory was wrong (it said Miranda comes after Charon; Umbriel does). The prompt now asks it to keep checked facts apart from remembered ones.
- It read UTC as local time and used an emoji. Each wake-up now shows the owner's local time, and the prompt asks for plain text.
- It believed messages wait for its next scheduled wake-up; they actually wake it within seconds. The prompt now says so.
- Cost: one 10-call wake-up used about 227k input tokens, because every call resends all earlier page fetches. Now only the latest tool result stays whole and long earlier ones are cut to 600 characters; in a fake 10-read wake-up that sent 36% of the characters. DeepSeek caches repeated prompt openings and bills those tokens far cheaper, so the untrimmed version cost less than its raw count suggested; the sleep line now shows how much was cached (`3081 in (2900 cached)`), and tokens from retried empty replies are counted too.
- Perro only saw the last 20 log events, about two chat exchanges (a reply makes ~9 events). Asked how long it had been alive, it dated its "earliest memory" to the last thing on its page, not its first wake-up. The page now has a "Recent conversation" section from the messages table (16 messages / 4,000 characters), and message events in the log show only their header.
- Told that SOUL.md is a file it can edit, it also wrote its notes into `workspace/notes.md` before using the notes field. The prompt now says notes aren't a workspace file.
